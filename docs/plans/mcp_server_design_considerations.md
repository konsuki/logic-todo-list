## A. 配備（どこで動かすか）

### A1. 実行環境

**論点**: MCP サーバーをどのマシン上で、どのようなプロセスとして実行するか。

| 選択肢 | 説明 | 検討すべきこと |
|---|---|---|
| **ローカルプロセス** | ユーザーの Mac 上で `node` または `python` プロセスとして常駐させる | AI エージェント（Claude Code 等）と同じマシンで動作するため、`localhost` のファイルシステムに直接アクセス可能。最もシンプル |
| **リモートサーバー** | クラウド上にデプロイし、HTTPS 経由でアクセスする | ビジューのデータはブラウザの localStorage にあるため、リモートからの直接アクセスは不可能。別途データ同期の仕組みが必要になる |

**現時点での妥当な初期選択**: ローカルプロセス。ビジューのデータはブラウザ localStorage に閉じているため、リモート化するにはデータ同期の課題を先に解決する必要がある。

### A2. データアクセス経路

**論点**: ビジューの全ツリーデータはブラウザの `localStorage`（キー: `logido_tree_data`）に JSON 文字列として保存されている。MCP サーバー（＝ Node.js/Python の常駐プロセス）がこのデータにどうアクセスするか。

| 選択肢 | 説明 | メリット | デメリット |
|---|---|---|---|
| **ブラウザ拡張機能** | MCP サーバーとは別にブラウザ拡張を作り、`localStorage` を読み取って MCP サーバーに HTTP で渡す | `localStorage` に最も確実にアクセスできる | ブラウザ拡張の開発・配布が必要。アーキテクチャが複雑化する |
| **ファイル書き出し方式** | ビジューのアプリ自体に「MCP 用にデータを JSON ファイルとしてエクスポートする」機能を追加する。MCP サーバーはそのファイルを読む | 実装が単純。ビジュー側の改修も小さい | ユーザーが手動エクスポートする必要がある場合、自動化されない |
| **自動エクスポート方式（推奨候補）** | ビジュー側に `useEffect` を追加し、`nodes` が更新されるたびに自動的に特定のファイルパス（例: `~/.bizyu/tree_data.json`）へ書き出す。MCP サーバーはそのファイルを読む | 常に最新データに自動追従する。ユーザーの手動操作不要 | ビジューがブラウザで動いている間のみ更新される。ファイルパスをハードコードする必要がある |
| **SQLite / ファイル監視** | `localStorage` のキーに対応するブラウザの保存ファイル（Chrome なら `LevelDB`、Firefox なら `webappsstore.sqlite`）を直接読む | ビジュー側の改修がゼロ | ブラウザの内部実装に依存し、ブラウザの種類・バージョンでファイル形式が変わるため極めて脆弱 |

**現時点での推奨初期方針**: 「自動エクスポート方式」。ビジュー側に、`nodes` の変更を検知して `~/.bizyu/tree_data.json` に書き出すフックを追加する。

### A3. トランスポート（通信方式）

**論点**: MCP サーバーと AI エージェント（MCP クライアント）の間の通信方式を何にするか。

| 選択肢 | 説明 | 適した場面 |
|---|---|---|
| **stdio（標準入出力）** | AI エージェントが MCP サーバーを子プロセスとして起動し、標準入出力で JSON-RPC をやり取りする | AI エージェントがローカルで動いている場合。MCP のデフォルト方式。Claude Code の MCP 連携もこれを想定 |
| **SSE / HTTP** | MCP サーバーが HTTP サーバーとして常駐し、AI エージェントが HTTP リクエストで通信する | リモート接続が必要な場合。または複数の AI エージェントから同時に使う場合 |

**現時点での初期選択**: `stdio`。ビジューは完全ローカルのアプリであり、AI エージェントも同一マシン上の Claude Code を想定するため。

## B. ツール設計（どんな操作を提供するか）

### B1. 読み取り系ツール（必須）

**論点**: AI エージェントがビジューのツリーデータから情報を得るために、どのような単位でデータを取得できるツールを提供すべきか。

以下に候補となるツールと、それぞれの「どういう時に・どういう目的で」使われるかを記す。

#### (1) `get_full_tree` — ツリー全体の取得

- **どういう時に**: AI エージェントが依頼されたタスクの規模や文脈を全体的に把握したい時。たとえば「このプロジェクト全体を見て、今どのタスクに着手すべきか提案して」といった俯瞰的な依頼を受けた場合。
- **どういう目的で**: 全ノードの親子関係・進捗・ステータスを俯瞰し、依頼内容がツリー全体の中でどの位置にあるのかを AI が自律的に判断するため。
- **リスク**: ツリーが巨大な場合、AI のコンテキストウィンドウを圧迫する。

#### (2) `get_node_context` — 指定ノードのコンテキスト取得

- **どういう時に**: AI エージェントが「このタスクをやって」という依頼を受け、そのタスクに対応するビジュー上のノードが特定された時。
- **どういう目的で**: 指定ノードの (a) 祖先パス（Why: 上位目的の連鎖）、(b) 子ノード一覧（How: 手段のリスト）、(c) 詳細意図（intent）、(d) 依存関係（dependsOn）、(e) 兄弟ノード（実行順序上の位置）をワンセットで取得し、そのタスクの背景を完全に理解するため。
- **出力イメージ**:
  ```
  === 選択ノード ===
  Title: "CI/CDパイプラインを構築する"
  Type: ACTION | Status: TODO | Progress: 0%
  Intent: "現状手動デプロイに30分かかっているのを5分未満に短縮したい。GitHub Actionsを使う前提。"
  Phase: EXEC

  === Why?（目的の連鎖）===
  [GOAL] 自社サービスをローンチする
    └─ [STRATEGY] 技術的な基盤を整える
         └─ [ACTION] ★ CI/CDパイプラインを構築する ← 現在地

  === How?（手段）===
  （このノードは末端のため子なし）

  === 依存関係（dependsOn）===
  先行: [ACTION] AWSアカウントを開設する（DONE ✓）
  → このタスクはロック解除済み（着手可能）

  === 兄弟ノード（実行順序）===
  1. AWSアカウントを開設する（DONE ✓）
  2. ★ CI/CDパイプラインを構築する（TODO）← 現在地
  3. 監視体制をセットアップする（TODO）
  ```

#### (3) `search_nodes` — キーワードによるノード検索

- **どういう時に**: AI エージェントがユーザーの依頼文から、どのノードが該当するかを自分で見つける必要がある時。ユーザーが「CI/CDのやつお願い」のようにノードの正式名称と異なる表現で依頼した場合。
- **どういう目的で**: キーワード検索によって候補ノードを列挙し、AI がその中から依頼文に最も合致するノードを同定するため。

#### (4) `get_node_summary` — ツリーの要約一覧

- **どういう時に**: ツリー全体を取得するには大きすぎるが、全体像を俯瞰したい時。
- **どういう目的で**: 全ノードを `[type] title (status, progress%)` の一行形式で一覧し、AI がコンテキストを節約しつつ全体構造を把握するため。

### B2. 書き込み系ツール（要否の判断）

**論点**: MCP サーバー経由でビジューのツリーに変更を加える（ノード追加・更新・完了など）機能を提供するか。

| 判断軸 | Read-Only 派 | Read-Write 派 |
|---|---|---|
| **複雑さ** | シンプル | ビジュー側と MCP サーバー側の双方向同期が必要 |
| **データ整合性** | 問題なし（読み取りのみ） | MCP 経由の変更をビジュー側に即時反映する仕組みが必要。競合（ユーザーが同時にビジューを操作している場合）の解決も必要 |
| **ユースケース** | AI が背景を理解してコードを書く、という当初目的には十分 | AI が「タスク完了」を自動報告したり、AI 自身がサブタスクを追加したりできる |

**現時点での初期判断**: **Read-Only から始める**。当初の目的（「AI エージェントに前提情報を渡す」）には読み取り系だけで十分であり、書き込みは複雑さを大幅に増すため、まずは読み取りに絞って価値検証する。

### B3. 検索・照会系ツール（補助）

- **`list_root_goals`**: 全 GOAL（ルートノード）の一覧を返す。AI が「どのプロジェクトについての依頼か」を最初に特定するために使う。
- **`get_node_by_id`**: ノード ID を直接指定して単一ノードの全フィールドを取得する。AI がすでに ID を把握している場合の高速な再取得。

## C. データ形式（AI にどう見せるか）

### C1. ツリー全体 vs サブツリー

**論点**: `get_full_tree` や `get_node_context` で返すデータは、ツリー全体か、指定ノードを中心としたサブツリーか。

- **サブツリー方式（推奨）**: `get_node_context` では、指定ノードからルートまでの祖先パス（Why）と、直下の子ノード一覧（How）、兄弟ノード（order でソート）に絞る。これにより、巨大なツリーでもコンテキストサイズが指定ノードの周辺に限定される。
- **全体方式**: 小規模なツリー（ノード数が数十程度）であれば、全体を返すほうが AI が自律的に判断できる幅が広がる。`get_node_summary` でまず全体の要約を見てから、必要に応じて個別ノードのコンテキストを取得する、という二段階の使い方をデフォルトとする。

### C2. ノードデータのシリアライズ粒度

**論点**: 各ノードの全フィールド（§13 のデータモデル参照）のうち、どれを MCP のレスポンスに含めるか。

| フィールド | 含めるか | 理由 |
|---|---|---|
| `id` | ✅ 必須 | AI が後続のツール呼び出しでノードを指定するために必要 |
| `parentId` | ✅ 必須 | 親子関係の表現に必須 |
| `type` | ✅ 必須 | GOAL/STRATEGY/ACTION の区別は前提情報の中核 |
| `title` | ✅ 必須 | ノードの表示名 |
| `description` | ✅ 含める | 補足情報として価値がある |
| `intent` | ✅ **最重要** | この提案の核。AI に渡す前提情報のうち最も価値が高い |
| `status` | ✅ 含める | TODO/IN_PROGRESS/DONE は着手可否の判断に使う |
| `progress` | ✅ 含める | 進捗の把握に使う |
| `children` | ✅ 含める | 親子関係の表現に必須 |
| `dependsOn` | ✅ 含める | 実行順序制約の把握に必須 |
| `phase` | ✅ 含める | PREP/EXEC/REVIEW の把握に使う |
| `dueDate` | ⚠️ 含める | 期限情報は有用だが、null が大半なら省略可 |
| `order` | ✅ 含める | 兄弟ノード間の順序把握に必須 |
| `hidden` | ❌ 省く | hidden=true のノードはそもそも出力対象外（`activeChildren` の扱いに従う） |
| `deletedAt` | ❌ 省く | 削除済みノードは出力対象外 |
| `metadata.createdAt` | ⚠️ 任意 | 時系列の把握に有用だが必須ではない |
| `metadata.updatedAt` | ⚠️ 任意 | 同上 |

### C3. コンテキストサイズ制御

**論点**: ツリーが大きい場合（例: 100ノード以上）、全データを一度に返すと AI のコンテキストウィンドウを圧迫する。どう制御するか。

- **要約モード**: `get_node_summary` では、`[GOAL] 自社サービスをローンチする (IN_PROGRESS, 45%)` のような一行形式で、全ノードをフラットに列挙する。これだけで全体構造の把握には十分。
- **段階的詳細化**: AI はまず `list_root_goals` でプロジェクトを特定 → `get_node_summary` で全体を俯瞰 → 気になるノードを `get_node_context` で深掘り、という段階を踏む。
- **最大深さ制限**: `get_node_context` の祖先パス表示において、深さが極端に深い場合は中間を省略（`...`）するオプションを設ける。

## D. ノード特定（AI がどう目的のノードを見つけるか）

### D1. ノード特定の方式

**論点**: ユーザーが AI エージェントに「CI/CDのやつお願い」と言った時、AI はビジュー上のどのノードが該当するかをどうやって見つけるか。

| 方式 | 説明 | メリット | デメリット |
|---|---|---|---|
| **タイトル検索（部分一致）** | `search_nodes` ツールがノードタイトルに対して部分一致検索を行い、候補を返す | 実装が簡単。日本語対応も問題ない | あいまいな依頼文（「あのデプロイのやつ」）ではヒットしない可能性がある |
| **intent 検索** | ノードの `intent`（詳細意図）フィールドも検索対象に含める | intent には自然文で背景が書かれているため、あいまいな依頼文とのマッチ率が上がる | intent が空のノードも多い場合、効果が限定的 |
| **ツリー全体を読ませて AI 自身に選ばせる** | `get_node_summary` で全ノード一覧を取得し、AI 自身が最も適切なノードを推論する | 最も高精度。人間と同じように「文脈判断」ができる | ツリーが大きいとコンテキストを消費する |

**現時点での初期方針**: 3つすべてを組み合わせる。`search_nodes`（タイトル＋intent 全文検索）を一次フィルターとして提供しつつ、小規模ツリーでは `get_node_summary` で全ノードを AI に読ませる併用を基本とする。

### D2. 曖昧検索と候補提示

**論点**: `search_nodes` の結果が複数ヒットした場合、どのように AI が正しいノードを選べるようにするか。

- 各候補に、**祖先パス（例: 「自社サービスをローンチする > 技術的な基盤を整える > CI/CDパイプラインを構築する」）**を付与して返す。これにより AI は単なるタイトル一致ではなく、ツリー上の位置づけを見て判断できる。
- スコアリング（タイトル完全一致 > タイトル部分一致 > intent 部分一致）を実装し、ソートして返す。

## E. 運用ルールの伝達（ツリーの読み方をどう教えるか）

### E1. ルール記述の埋め込み先

**論点**: ビジューのツリーが「どういうルールで構築されているか」（自動型昇格、ボトムアップ進捗計算、依存ロック、hidden/deletedAt の除外 など）を、AI エージェントにどのタイミングで伝えるか。

| 方式 | 説明 |
|---|---|
| **MCP サーバーのシステムプロンプト的レスポンス** | 最初のツール呼び出し時や、専用の `get_tree_rules` ツールを呼び出した時に、ルール一覧を返す |
| **各ツールのレスポンスに毎回埋め込む** | `get_node_context` の結果に、進捗計算ルールや依存ロックの説明をフッターとして付与する |
| **Claude Code の MCP サーバー記述（`description`）に含める** | MCP のツール定義の `description` フィールドに簡潔なルールを書いておく |

**現時点での初期方針**: **専用ツール `get_tree_rules` を設ける**。AI エージェントは最初にこのツールを呼び出して「データの読み方」を理解してから、実際のツリーデータにアクセスするという流れを推奨する。各ツールの description にも要点を記述する。

### E2. 伝達すべきルールの列挙

AI エージェントがビジューのツリーデータを正しく解釈するために知っておくべきルール：

1. **ノードタイプの意味**: GOAL（最終目標）→ STRATEGY（戦略）→ ACTION（具体行動）の三段階。上位ほど抽象的、下位ほど具体的。
2. **自動型昇格**: ACTION に子が追加されると自動的に STRATEGY になる。
3. **進捗計算**: 親の progress はアクティブな子ノードの progress の平均値。手動設定不可。
4. **ステータス自動更新**: progress=100 → DONE, 0<progress<100 → IN_PROGRESS, progress=0 → TODO。
5. **アクティブノード**: `hidden` または `deletedAt` が設定されたノードは進捗計算と表示から除外される。
6. **依存ロック**: `dependsOn` のいずれかが DONE でない場合、そのノードはロックされ完了操作ができない。
7. **execution order**: 兄弟ノード間は `order` フィールドの昇順で実行順序が決まる。

## F. データ鮮度・一貫性

### F1. localStorage からの読み取りタイミング

**論点**: 自動エクスポート方式（A2 参照）を採用した場合、以下のような「データが最新でない」リスクにどう対処するか。

- ビジューを開いていない状態で AI エージェントが MCP サーバー経由でデータを取得 → 最後にビジューを閉じた時点の古いデータを読んでしまう
- ビジューでタスクを編集した直後、まだファイル書き出しが完了していないタイミングで MCP サーバーが読み取り → 更新前のデータを読んでしまう

**対策案**:
- MCP サーバーのレスポンスに `data_exported_at`（ファイルの最終更新日時）を含め、AI が「このデータは X 分前のスナップショットです」と認識できるようにする。
- ビジュー側のエクスポートを `requestAnimationFrame` ではなく同期的な `useEffect` で行い、書き込み遅延を最小化する。

## G. セキュリティ・認可

### G1. アクセス制御の要否

**論点**: ビジューのツリーデータには、プロジェクトの機密情報（未公開の製品名、顧客名、戦略情報など）が含まれる可能性がある。MCP サーバー経由でこのデータが外部に漏洩しないようにする必要があるか。

- **現状**: MCP サーバーは stdio で同一マシン上の AI エージェントとのみ通信する。外部ネットワークには一切データを送信しない設計であれば、漏洩リスクは低い。
- **注意点**: MCP サーバーのレスポンスが AI エージェント（Claude Code）を経由して Anthropic の API サーバーに送信される。これは AI エージェント利用の一般的なデータフローであり、MCP サーバー固有の問題ではないが、意図しないデータ送出を防ぐために、**読み取り範囲を明示的に指定できるパラメータ**（特定の GOAL 配下のみ、など）を設けることは検討に値する。
- **初期判断**: 初期バージョンではアクセス制御は設けず、全ツリーデータを MCP サーバーが読み取れる状態とする。ビジューのデータはすべてローカルに閉じており、リモート送信は AI エージェント側の設定に委ねられるため。

## H. 拡張性（将来の機能追加余地）

### H1. 双方向連携（AI がタスクをビジューに書き戻す）

**論点**: Read-Only で始めた後、将来的に AI エージェントがビジューにタスクを追加・更新できるようにする場合の設計上の布石。

- MCP ツールとして `add_node`、`update_node`、`toggle_node_status` などを追加する。
- その際の最大の課題は **双方向同期**: MCP 経由で変更したデータを、ブラウザで開いているビジューにどう即時反映するか。
  - 案1: ビジュー側にファイル監視（`~/.bizyu/tree_data.json` の変更をポーリング）を追加する。
  - 案2: WebSocket で MCP サーバーとビジューが常時接続し、変更をプッシュ通知する（アーキテクチャが大幅に複雑化）。
  - 案3: 「MCP 経由の書き込みは、ビジューを開き直した時に反映される」という割り切りで済ませる。
- **初期判断**: 案3（再読み込み時反映）で妥協する。双方向リアルタイム同期はスコープ外とする。

### H2. 複数プロジェクト対応

**論点**: ビジューのデータモデルでは、複数の GOAL（ルートノード）が同一の `nodes` オブジェクト内に共存できる。MCP サーバーはこのマルチプロジェクト構造を前提として設計する必要がある。

- `list_root_goals` ツールで全 GOAL を列挙し、AI が「どのプロジェクトの話をしているか」を最初に絞り込めるようにする。
- `get_node_context` では、指定ノードが属する GOAL を自動判定し、他の GOAL の情報は混ぜない。

## I. 実装技術の選択

### I1. 言語

| 選択肢 | メリット | デメリット |
|---|---|---|
| **Node.js (JavaScript)** | ビジュー本体と同じ言語。`treeLogic.js` の純粋関数をそのまま再利用できる。開発者が既存コードを流用しやすい | 特になし |
| **Python** | MCP の Python SDK が充実している。ファイル読み取りがシンプル | ビジューのロジック（進捗計算など）を Python で再実装する必要がある（または計算済みの値を信頼してそのまま返すだけにする） |
| **Go / Rust** | 高速・軽量 | ビジューのエコシステムと無関係。過剰設計の可能性が高い |

**現時点での初期選択**: **Node.js**。`treeLogic.js` の再利用が可能で、開発者にとって馴染みのある言語であるため。

### I2. MCP SDK

- **Node.js**: `@modelcontextprotocol/sdk` を使用。
- **実装の基本構造**:
  ```js
  import { Server } from "@modelcontextprotocol/sdk/server/index.js";
  import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
  import { CallToolRequestSchema, ListToolsRequestSchema } from "@modelcontextprotocol/sdk/types.js";

  const server = new Server({
    name: "bizyu-mcp",
    version: "1.0.0",
  }, {
    capabilities: { tools: {} }
  });

  // ツール定義 + ハンドラを登録
  server.setRequestHandler(ListToolsRequestSchema, async () => ({ tools: [...] }));
  server.setRequestHandler(CallToolRequestSchema, async (request) => { ... });

  // stdio で起動
  const transport = new StdioServerTransport();
  await server.connect(transport);
  ```

## 備考

- 本ドキュメントは「論点整理」であり、各論点の最終決定ではない。実装を開始する前に、各論点について決定を行い、別途「実装プラン」ドキュメントに落とし込むことを想定している。
- MCP サーバーの実装そのものはビジュー本体のリポジトリとは別リポジトリ（例: `bizyu-mcp-server`）で管理することを推奨する。自動エクスポート機能のみビジュー本体に追加する。
