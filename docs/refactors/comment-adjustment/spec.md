# コメントの過不足を調整する

## 1. 誰の、どんな困りごとを解決するのか

- **誰**: 本アプリを就職活動のポートフォリオとして提示する開発者。およびコードレビューする評価者。
- **困りごと**: コードのコメントに「過不足」がある。コードの言い換えに過ぎない冗長コメントは読み手のノイズになり、一方で「なぜそうしたか」という意図が書かれていない箇所は、初見の評価者が処理の意図を追えない。必要十分なコメント密度に揃える。**実行時の挙動は一切変えない。**

## 2. 現状の調査結果

- **ロジックモジュール（lib/）**: JSDoc が充実しており、ほぼ問題なし（treeLogic 分割時に付与済み）。
- **コンポーネント（.jsx）**: JSDoc がほぼ無く、役割の説明が不足気味。
- **過剰コメント**: 少数（`TreeView.jsx` / `useTodoTree.js` に「コードの言い換え」が一部）。
- **付随する軽微な可読性改善（インライン style 等）**: 本タスクでは扱わない（「整形と最終検証」タスクへ引き継ぎ済み）。

## 3. 変更内容（2 分類）

### A. 過剰・冗長コメントの削除

- 「コードの言い換え」になっているコメントを削除する（コードから自明なものに限定）。
- **過剰削除を避ける**: 非自明な処理の補足として有用なコメントは残す。削除対象は「本当にコードから自明」なものに限定する。

### B. 不足コメント・JSDoc の補完

- 意図が伝わりにくい箇所に「なぜ」を説明するコメントを追加する。
- 主要なコンポーネント・フックに JSDoc（1 行の役割説明）を追加する。
- **最低限に留める**: 全関数に付けるのではなく、役割が明確でない主要なものに限定する。

## 4. 普通ではないケース・境界条件

- **挙動非変更が最優先**: コメントの追加・削除のみで、ロジック・JSX は 1 文字も変更しない。
- **削除と追加のバランス**: 「削除しすぎて意図が失われる」「追加しすぎてノイズになる」の両方を避ける。

## 5. 優先順位・本当に必要なもの

- **最優先**: 挙動非変更。
- **DoD**: `npm run lint` が exit 0、`npm run test:run` が 53 件 pass、`npm run build` が成功する。

## 6. 完了の定義（DoD）

- 過剰・冗長なコメントが削除されている。
- 意図が伝わりにくい箇所に「なぜ」のコメント・JSDoc が追加されている。
- `npm run lint` / `npm run test:run`（53 件）/ `npm run build` が全て通る。
