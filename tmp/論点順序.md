# 論点順序：Google AI 検索履歴の合理的なディレクトリ構造設計

## 検討の順序

各論点には依存関係がある。以下の順序で検討することで、先行する結論が後続の判断材料となり、手戻りを最小化できる。

---

### 第1論点：実データの全体像と分類軸の把握（論点1）

**採用理由**: すべての設計判断の材料となる基礎情報。データの実態を知らずに構造を決めることはできない。この論点で得られた「903件・トピック多様・連鎖質問あり」という知見が、後続すべての論点の前提となる。

**【詳細手順】**

**Step 1: HTML ファイルの基本情報を取得する**
- 入力: `/Users/konnsuki/Googleマイアクティビティ/AI モード/マイアクティビティ.html`
- 操作: `wc -l` で行数、`ls -la` でファイルサイズを確認。`head -c 5000` で先頭部を読み、HTML 構造の特徴（CSS フレームワーク、文字コード宣言など）を把握する。
- 出力: ファイル規模（行数・バイト数）と基本構造メモ。

**Step 2: HTML の DOM 構造を解析し、エントリの繰り返しパターンを特定する**
- 入力: HTML 全体
- 操作: `grep` で class 名の出現頻度を集計し、リスト表示に使われている CSS クラス（`mdl-grid`, `outer-cell`, `content-cell` など）を特定する。1エントリがどの HTML 要素の組み合わせで構成されているかを特定する。
- 出力: エントリ抽出のための正規表現パターン（例: `class="mdl-typography--title">(.*?)</div>.*?content-cell ... body-1">(.*?)</div>`）

**Step 3: 全エントリを抽出し、件数・期間を集計する**
- 入力: HTML 全体
- 操作: Step 2 のパターンを用いて Python スクリプトで全エントリを抽出。日時情報を正規表現で取得し、月別・週別の件数を集計する。
- 出力: 総エントリ数、期間（開始日〜終了日）、月別ヒストグラム。

**Step 4: エントリの内容をサンプリングし、トピックの多様性を把握する**
- 入力: 抽出した全エントリ
- 操作: 先頭から50件、末尾から50件、ランダム50件の合計150件について、検索クエリ（プロンプト）の内容を読み、どのようなジャンル・質問タイプが存在するかを観察する。目視でパターンを分類する。
- 出力: トピックジャンルの暫定リスト（例: 技術, 歴史, 語源, 地理, 雑学, 実務調査, ツール探し, ポップカルチャー...）と、それぞれの出現頻度感覚。

**Step 5: 分類軸の候補を列挙し、上位目標との整合性を評価する**
- 入力: Step 3〜4 の集計・観察結果、上位 GOAL「頭よく見えるようになる」〜「Objibianで知識整理」
- 操作: 以下の観点で分類軸の候補を列挙し、それぞれの pros/cons を比較する:
  - 時間軸: 機械分類可能だが、知識の引き出しには不向き
  - トピック軸: 知識整理に最適だが、分類判断に人間/AIが必要
  - 質問型軸: 機械分類可能だが粒度が粗すぎる
  - 実用性軸: 有用だが主観的で分類困難
- 出力: 推奨される主分類軸（トピック軸）と補助分類軸（時間軸、連鎖質問グループ化）の組み合わせ案。

**Step 6: 結論の記述**
- 入力: Step 5 の評価結果
- 操作: 以下の形式で結論をまとめる:
  - 採用する主分類軸: トピック／ドメイン
  - 補助分類軸: 時間（ソートキーとして保持）、連鎖質問（同一トピックのグループ化）
  - 分類の難易度と対応策: AI（Claude）による自動分類＋人間による確認
  - 903件のデータ特性サマリー（件数・期間・トピック多様性）
- 出力: 論点1の結論（後続論点の入力となる）

---

**📌 結論（論点1）**

- **採用する主分類軸**: トピック／ドメイン軸。上位 GOAL「使える知識を整理して定着させる」に対して、時間軸では不十分であり、知識の意味的なまとまりで分類する必要がある。
- **補助分類軸**:
  - 時間（日付）: 全ファイル名のプレフィックスとして保持し、時系列ソート・フィルタを可能にする。
  - 連鎖質問のグループ化: 同一トピックを掘り下げる連続質問は、同一ディレクトリまたは相互リンクで関連付ける。
- **データ特性サマリー**:
  - 件数: 903 件
  - 期間: 2022/02（1件の外れ値）〜 2026/07。本格利用は 2025/09 以降。
  - 月間ペース: 直近3ヶ月で月 118〜175 件。増加傾向。
  - トピック多様性: キーワードベースの簡易分類では 10 カテゴリ程度に分かれるが、673 件（75%）は単純なキーワードマッチでは拾えず、非常に多様。AI による文脈理解が必須。
  - 主要ジャンル（サンプル観察から）: 技術・プログラミング、語源・由来、歴史・社会、地理・文化、法律・実務、料理・生活、数学・論理、エンタメ・ポップカルチャー、ビジネス・経済、言語・翻訳
- **分類の現実解**: 全件を完全手動分類するのは非現実的（903 件 × 1 分 ＝ 約 15 時間）。Claude Code にプロンプト一覧を渡して AI 分類させ、ユーザーが確認・修正するハイブリッド方式を採用する。

### 第2論点：ディレクトリ階層の深さと命名規則の設計（論点2）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点2）**

**階層数**: **2 階層**（トップレベルカテゴリ → 個別ファイル）。一部の大きなカテゴリはサブカテゴリ（第2階層）を持つことで実質 3 階層になる。

**命名規則**:
- **ディレクトリ名**: 日本語（Obsidian での直感的ブラウジングを優先）。スペースを含まない、または中黒（・）区切り。
- **ファイル名**: `{YYYY-MM-DD}_{slug}.md` 形式。slug はクエリから生成した簡潔なローマ字または英語（例: `2026-07-27_ninchi-kino-teika-sagi.md`）。

**ディレクトリ構造（完全ツリー）**:
```
google-ai-history/
├── _index.md                          ← 全トピックの索引・Dataviewクエリ
├── _inbox/                             ← 未分類の新着エントリ一時置き場
├── 技術・プログラミング/
│   ├── API・通信/
│   ├── AI・LLM/
│   ├── コマンド・シェル/
│   └── 言語・フレームワーク/
├── 語源・由来/
├── 歴史・社会/
├── 地理・文化・言語/
├── 科学・自然/
├── 数学・論理/
├── 法律・ビジネス/
├── 料理・生活/
├── エンタメ・ポップカルチャー/
├── ファッション・衣類/
├── 言語・翻訳/
├── メディア・出版/
└── その他/                             ← どのカテゴリにも入らないもの
```

**注記**: 上記のカテゴリは仮置きであり、実際の AI 分類結果を見て調整する。特に「語源・由来」は 82 件（キーワードマッチ分のみ）と多く、さらに細分化される可能性が高い。

### 第3論点：1件あたりのファイル形式とテンプレート設計（論点3）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点3）**

**ファイル形式**: **Markdown（.md）**。Obsidian のネイティブ形式であり、フロントマター・内部リンク・タグのすべてが機能する。

**テンプレート**:
```markdown
---
date: 2026-07-27T11:25:50+09:00
source: google-ai-mode
topic: [法律, 高齢者]
tags: [準詐欺罪, 刑法248条, 認知症]
related: []
---

# 認知機能が低下している高齢者が詐欺罪として立件される場合はありますか

## 質問（プロンプト）
認知機能が低下している高齢の人が不自然なほど、あまりにも利用者に多いなどの場合、詐欺罪として立件される場合はありますか

## AI の回答
（Google AI Mode の回答全文。Markdown に変換して保持）

## 補足・考察
（ユーザーが後から追記するための空欄セクション）
```

**フィールド設計意図**:
| フィールド | 用途 | 検索性 |
|-----------|------|--------|
| `date` (ISO 8601) | Dataview ソート・時系列フィルタ | `date >= 2026-07-01` |
| `source` | データソース識別（将来拡張用） | `source: google-ai-mode` |
| `topic` (配列) | 主分類（ディレクトリ構造と連動） | `topic: 法律` |
| `tags` (配列) | 粒度細かいキーワード | `tags: 詐欺罪` |
| `related` (配列) | 関連ファイルへの内部リンク | Obsidian グラフビュー |

### 第4論点：Objibian（Obsidian）との統合設計（論点5）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点4）**

**配置場所**: 既存の Objibian Vault 直下に `google-ai-history/` ディレクトリを作成する。独立 Vault より、既存知識ベースとの横断リンクが可能な点を重視。

**プラグイン連携**:
- **Dataview**: 以下のクエリ例を `_index.md` に埋め込む:
  ```dataview
  TABLE date, tags FROM "google-ai-history" WHERE contains(topic, "法律") SORT date DESC
  ```
- **Templates**: 新規エントリ手動追加用に Obsidian テンプレートとして論点3のテンプレートを保存。
- **Graph View**: `related` フィールドの内部リンクが自動的にグラフに反映される。
- **Tag Pane**: `tags` フロントマターが自動的にタグペインに表示される。

**_index.md の設計**:
- 全トピックカテゴリへのリンク一覧
- Dataview クエリ（最近追加されたエントリ、トピック別件数集計）
- Inbox の未整理件数表示

### 第5論点：Claude Code からの検索・参照を容易にする仕組み（論点6）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点5）**

**主要な検索パターン**:
1. **トピック別検索**: `grep -l "topic:.*法律" google-ai-history/**/*.md`
2. **キーワード横断検索**: `grep -l "詐欺罪" google-ai-history/**/*.md`
3. **日付範囲検索**: `ls google-ai-history/**/2026-07-*.md`
4. **インデックス経由探索**: Read `google-ai-history/_index.md` → カテゴリ確認 → 対象ファイルを Read

**推奨探索フロー**（Claude Code が自律的に使うパターン）:
1. ユーザーが「○○について調べたことある？」と質問
2. Claude Code が `_index.md` を Read してカテゴリ把握
3. 関連カテゴリのファイル一覧を Glob で取得
4. 絞り込みに Grep（フロントマター＋本文）
5. ヒットしたファイルを Read して回答

**オプション（後日実装）**: `/knowledge` スラッシュコマンドを作成し、上記フローを自動化。

### 第6論点：HTMLからの抽出・変換方法（論点4）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点6）**

**抽出方法**: Python スクリプト + 正規表現（`re.findall` で `mdl-typography--title` + `content-cell ... body-1` のペアを抽出）。

**変換ルール**:
| 入力（HTML） | 出力（Markdown） |
|-------------|-----------------|
| `\xa0` | 通常スペースに変換 |
| `<br>` / `<br/>` | 改行 |
| `<a href="URL">text</a>` | `[text](URL)` |
| `<b>` / `<strong>` | `**text**` |
| `<FollowUp>...</FollowUp>` | `> ...`（引用ブロック） |

**出力先**: Phase 1 では全ファイルを `google-ai-history/_inbox/` にフラット出力。トピック分類後に正規ディレクトリへ移動。

**ファイル名生成**: `{YYYY-MM-DD}_{slug}.md`。slug は検索クエリの先頭 5 単語程度からローマ字で自動生成。ユニーク性確保のため、同一日付の重複時は `_2`, `_3` サフィックスを付与。

**品質確認**: サンプル 20 件を Obsidian で開き、フロントマターのパース、本文の改行・リンク表示、日本語文字化けの有無を確認する。

### 第7論点：未知の新トピック追加時の運用ルール（論点7）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点7）**

**1. Inbox 運用ルール**:
- 新規エントリはすべて `_inbox/` に投入
- 週1回、Claude Code に Inbox 内エントリの分類を依頼
- Topic/tags 付与済みのエントリを適切なディレクトリに移動

**2. カテゴリ追加・分割ルール**:
- 既存カテゴリに明確に属さないエントリ → `その他/` に仮置き
- 同一傾向のエントリが `その他/` に **5 件以上**溜まったら新カテゴリ新設
- 1カテゴリ内が **50 件超**になったらサブカテゴリ分割を検討

**3. タグ運用ルール**:
- タグは自由に追加（制限なし）
- 月1回、Dataview で使用タグ一覧を確認し表記揺れを統一
- 1回しか使われていないタグは統合または削除

**4. 定期メンテナンス**:
| 頻度 | 作業 | 所要時間 |
|------|------|---------|
| 週次 | Inbox 振り分け | 10分 |
| 月次 | タグ整理・構造見直し | 30分 |
| 四半期 | 大規模構造再編の検討 | 1時間 |

### 第8論点：優先順位付けと段階的整理の戦略（論点8）

**【詳細手順】（略 ― 既に記述済み）**

---

**📌 結論（論点8）**

**実行ロードマップ**:
```
Step 0: 抽出・変換スクリプト作成（30分）
  ↓
Step 1: Phase 1 フラット Markdown 変換実行（1分）
  → 903 件の Markdown を _inbox/ に生成
  ↓
Step 2: ディレクトリ構造の空枠作成（5分）
  → mkdir で全カテゴリディレクトリを作成
  ↓
Step 3: AI によるトピック分類（15〜30分）
  → Claude Code に全プロンプト一覧を渡し、各エントリの topic/tags/slug を付与
  ↓
Step 4: 分類結果に基づくファイル移動（5分）
  → スクリプトで _inbox/ から各カテゴリディレクトリへ移動
  ↓
Step 5: _index.md 作成（10分）
  → 全トピックリンク + Dataview クエリ
  ↓
Step 6: Obsidian 設定（15分）
  → テンプレート登録、Dataview クエリ確認
  ↓
Step 7: 運用開始
  → 週次 Inbox 整理、月次タグメンテナンス
```

**合計所要時間**: **約 1〜1.5 時間**（AI 分類の確認時間を除く）

**最初に着手すべきタスク**: Step 0「抽出・変換スクリプトの作成」。すべての後続ステップの前提となる。
