# 論点一覧：Google AI 検索履歴の合理的なディレクトリ構造設計

## 目標
Google AI 検索の履歴（903件のHTML）を、あとから参照・復習しやすい形に整理するディレクトリ構造を設計する。

## 論点

1. **実データの全体像と分類軸の把握**

**【論点の位置づけ】**
この論点は、ディレクトリ構造を設計するための「材料理解」にあたる。設計対象である 903 件の Google AI 検索履歴データが、どのような性質・分布・構造を持っているのかを正確に把握しなければ、それに適したディレクトリ構造を設計することは不可能である。この論点では「データをどう分類できるか（分類軸の候補）」を洗い出し、後続の論点（ディレクトリ階層の深さ、命名規則、ファイル形式など）の判断材料を提供することを目的とする。

**【データの物理的実態】**
- **ファイル**: `/Users/konnsuki/Googleマイアクティビティ/AI モード/マイアクティビティ.html`
- **サイズ**: 約 7.2MB、54,676行
- **形式**: Google Takeout の「My Activity > Search」からエクスポートされた単一の HTML ファイル。Material Design Lite（MDL）フレームワークでスタイリングされている。
- **エントリ数**: 903 件（`class="mdl-typography--title"` と `class="content-cell mdl-cell mdl-cell--6-col mdl-typography--body-1"` のペアとして抽出可能）
- **各エントリの内部構造**:
  1. タイトル部（`mdl-typography--title`）: 「AI モード」という固定ラベル
  2. 本文部（`content-cell ... body-1`）: 「『{検索クエリ}』を検索しました{日時} JST」という形式で始まり、その下に「プロンプト:」＋検索クエリ＋「検索の回答:」＋AI の回答全文が続く。
  3. 日時情報: `YYYY/MM/DD HH:MM:SS JST` 形式で本文部の冒頭に埋め込まれている。
  4. 一部エントリには `<FollowUp>` タグで囲まれた AI からの追加質問が含まれる。
  5. 回答部はプレーンテキストに近い HTML（改行 `<br>` やリンク `<a>` を含む）で書かれている。

**【データの時間的分布】**
月別のエントリ数は以下の通り。2022年2月に1件の古いエントリがあるが、本格的な利用は2025年9月以降で、2026年に入ってから急速に増加している（月100〜175件ペース）。
```
2022/02:   1件
2025/09:  23件, 2025/10:  23件, 2025/11:  27件, 2025/12:  69件
2026/01: 112件, 2026/02:  27件, 2026/03:  36件, 2026/04: 132件
2026/05: 175件, 2026/06: 118件, 2026/07: 160件
```

**【データの内容的特徴（サンプルから観察されたパターン）】**
実際の検索クエリ（プロンプト）は以下のような多様なジャンルに及んでいる：

1. **プログラミング・技術知識**: 「rest api以外のapiは存在しますか」「deepseek api」「プログラミングにおけるハンドラとは」
2. **歴史・教養**: 「『九十五箇条の提題』の発表（1517年）」「皇居は江戸城の跡地なのですか」
3. **語源・由来**: 「M-51 語源」「moonshot kimi 語源」「スコットランド 語源」「台東区の語源はなんですか」
4. **地理・社会**: 「ロンドンの空が灰色なのは地理的にどういう理由でしょうか」「アイルランドとイギリスは別の国ですか」「非上場で株を買えるのはだれ？」
5. **雑学・トリビア**: 「マクドナルドとバーガーキングが結婚したら…」「こち亀って日常アニメでシーズンものじゃないのに…」
6. **実用的な調査**: 「認知機能が低下している高齢の人が…詐欺罪として立件される場合はありますか」「短脊椎症 牛」
7. **ツール・アプリ探し**: 「ノートをディレクトリみたいに知識として整理できるアプリ…MCPみたいな機能があって…」
8. **コマンド解読**: 「$ du -sh ~/Library/Application\ Support/Epic/*/ ... ←←このコマンドの意味を教えてください」
9. **ポップカルチャー**: 「マーティー・マクフライとCalvin Kleinにはどんな関係がありますか」「白人英語のラップ」

**【分類軸の候補】**
このデータから抽出可能な分類軸として、以下が考えられる：

- **A. 時間軸（月次／週次）**: 日時情報が全エントリに存在するため、最も機械的に分類可能。ただし「知識の整理」という上位目的に対しては、時間軸だけでは不十分（「2026年4月に何を調べたか」はわかっても「あるトピックについて何を知っているか」はわからない）。
- **B. トピック／ドメイン軸**: 検索クエリの内容からトピックを推定し、「歴史」「技術」「語源」「地理」などに分類する。人間が判断する必要があり、自動化には AI による分類が必須。またトピック境界は曖昧になりがち（「スコットランドの語源」は「語源」か「地理」か）。
- **C. 質問の型軸（What/Why/How/YesNo）**: 「〜とは」「〜なぜ」「〜どうやって」「〜ですか」などの質問タイプで分類。機械的に判定可能だが、知識整理の単位としては粗すぎる。
- **D. 実用性／雑学軸**: 実務に直結する知識か、純粋な好奇心によるものか。これは後から知識を活用する際に「どの程度信頼性／深度が必要か」に影響するが、主観的で分類が難しい。
- **E. 構造化軸（単発質問 vs 連鎖質問）**: 同一トピックを掘り下げる連続した質問があるかどうか。例えば「上野はどんな町」→「台東区の語源」→「皇居は江戸城の跡地」→「浅草というのは区とかではないのですか」は明らかに東京の地理・歴史に関する連鎖的な興味から生じている。

**【上位目標との関係】**
このデータ整理の最終目的は「頭よく見えるようになる」→「使える知識を平均以上に持つ」→「Objibianで知識を整理」。したがって、単なるログのアーカイブではなく、**「後から検索・参照し、知識として定着させる」** ことを前提とした分類軸を選ぶ必要がある。この観点からは、**B（トピック軸）を主軸とし、E（連鎖質問のグループ化）で補完する** のが最も目的に合致すると考えられる。時間軸（A）は補助的なソートキーとして保持する価値がある。
2. **ディレクトリ階層の深さと命名規則の設計**

**【論点の位置づけ】**
論点1 で「トピック軸を主とし、連鎖質問を補完する」という方針が決まった場合、具体的にディレクトリを何階層にするか、各階層のディレクトリ名をどう命名するかのルールを定める必要がある。この論点は「構造の骨格」を決めるものであり、後続の全論点（ファイル形式、抽出方法、ツール統合）の土台となる。

**【設計上のトレードオフ】**
- **浅い階層（1〜2階層）**:
  - メリット: ファイルを見つけやすい、運用が単純、階層の迷子が起きにくい
  - デメリット: 1ディレクトリあたりのファイル数が多くなりすぎる（903件を10カテゴリに分けても1カテゴリ約90件）。目視でのブラウズが困難になる。
- **深い階層（3〜4階層）**:
  - メリット: 各ディレクトリが少数のファイルに絞られ、粒度の細かい整理が可能。「あのトピックについて何を知っているか」をディレクトリを見るだけで俯瞰できる。
  - デメリット: 分類の判断に迷うケースが増える。「この質問は A/B どちらのサブカテゴリに入れるべきか」という悩みが運用コストになる。また、深すぎると目的のファイルにたどり着くまでにディレクトリを何度も開く必要がある。

**【命名規則の検討事項】**
- **使用文字**: Objibian（Obsidian）は内部的にファイルパスを使用するため、スペース・日本語・特殊文字を含めても動作する。ただし、ターミナルや Claude Code からの操作を考慮すると、スペースを含む日本語名はエスケープが必要になり実用性が下がる。
- **可読性 vs 機械可読性**: `history/` `technology/` のような英字ディレクトリ名はスクリプト処理しやすいが、ユーザーがディレクトリ一覧を見たときに直感的に理解しにくい。一方 `歴史/` `技術/` のような日本語名はユーザーにとって直感的だが、スクリプトでのパス指定時に注意が必要。
- **Obsidian のリンクとの整合性**: Obsidian は `[[ページ名]]` で内部リンクを張る。ディレクトリ名を英語にするか日本語にするかは、Obsidian 内でのリンクの書きやすさに影響する。日本語名 + スペースありだと `[[歴史/ヨーロッパ/宗教改革]]` のように自然に書ける。英語名だと `[[history/europe/reformation]]` となる。
- **ID 付与の要否**: 各エントリに一意の ID（例: `20260727-112550` 日時ベース）を付与してファイル名に含めるか、クエリから生成したスラグ（例: `deepseek-api-toha`）を使うか。ID 方式は衝突がなく機械処理しやすいが、ファイル名から内容を推測できない。スラグ方式は可読性が高いが、同一トピックの別クエリとの区別が難しい。

**【上位目標との関係】**
「頭よく見えるようになる」ために「使える知識を持つ」ことが目的なので、ディレクトリ構造は **知識の引き出しやすさ** を最優先すべきである。つまり「この分野について何を知っているか」が見渡せる構造が望ましい。これはやや深め（2〜3階層）のトピック階層を支持する。

3. **1件あたりのファイル形式とテンプレート設計**

**【論点の位置づけ】**
HTML から抽出した個々の検索履歴を、どのようなファイル形式で保存するかを決める。これにより Objibian（Obsidian）での表示・編集体験や、Claude Code からの読み取りやすさが決まる。

**【候補となるファイル形式】**
- **Markdown（.md）** : Obsidian のネイティブ形式。リンク、タグ、フロントマター（YAMLメタデータ）が使える。Claude Code の Read ツールでも内容をそのまま理解できる。**全候補の中で最も統合性が高い。**
- **プレーンテキスト（.txt）** : 最も単純だが、Obsidian 内でリンクやフォーマットが使えないため、知識ネットワーク構築の妨げになる。
- **JSON（.json）** : 機械可読性は最高だが、Obsidian での閲覧・編集には不向き。Claude Code は読めるが、人間が直接読み書きするには実用的でない。
- **HTML（.html）** : 現状の形式。Obsidian は HTML をプレビュー表示できるが、編集・リンクには不向き。

**【Markdown テンプレートに含めるべきフィールド】**
以下の情報を YAML フロントマター＋本文に分割して格納する：
```markdown
---
date: 2026-07-27T11:25:50+09:00
source: google-ai-mode
topic: [法律, 高齢者, 詐欺]
tags: [準詐欺罪, 刑法, 認知症]
related: []
---

# 認知機能が低下している高齢の人が〜詐欺罪として立件される場合はありますか

## 質問（プロンプト）
認知機能が低下している高齢の人が不自然なほど、あまりにも利用者に多いなどの場合、詐欺罪として立件される場合はありますか

## AI の回答
（Google AI Mode の回答全文。改行・構造を Markdown に変換して保持）
```

**【フロントマターの設計意図】**
- `date`: ISO 8601 形式。Obsidian の Dataview プラグインでソート・フィルタ可能。
- `source`: データの出所。将来 Google AI Mode 以外の履歴（Gemini、ChatGPT 等）が追加された場合の識別用。
- `topic`: 論点1 の分類軸 B（トピック）に基づくカテゴリタグ。1ファイルに複数付与可能（MECE にこだわらず、複数の分類軸を許容する）。
- `tags`: より粒度の細かいキーワード。Obsidian のタグシステムと連携し、横断的な検索を可能にする。
- `related`: 関連する他ファイルへのリンク（`[[ファイル名]]` 形式）。連鎖質問や関連トピックをネットワーク化する。

**【上位目標との関係】**
このテンプレート設計は「Objibian で綺麗に勉強した知識を整理できる状態にする」を直接実現するものである。フロントマターによる構造化と、本文による自由な追記・編集を両立させることで、単なるログの転記ではなく「生きた知識ベース」への発展を可能にする。

4. **HTMLからの抽出・変換方法**

**【論点の位置づけ】**
論点3 で決めた Markdown テンプレートに従って、実際の HTML ファイル（7.2MB）から 903 件のエントリを抽出し、個別の Markdown ファイルに変換する具体的な方法を決める。この論点は「設計」と「実行」の橋渡しとなる。

**【技術的アプローチの選択肢】**
- **Python スクリプトによる一括変換**:
  - HTML パースには `BeautifulSoup4` または Python 標準ライブラリの `html.parser` + 正規表現を使用。
  - 各エントリの抽出ロジックは論点1で特定した構造（`mdl-typography--title` → `content-cell ... body-1`）を使う。
  - 出力先は論点2で決定するディレクトリ構造に従う。
  - メリット: 完全自動化。903 件を数秒で処理可能。再実行も容易。
  - デメリット: トピック分類の自動化には AI（Claude API など）の呼び出しが必要。コストがかかる。

- **段階的アプローチ（推奨）**:
  1. **Phase 1: 機械的抽出**: Python スクリプトで全 903 件を日付ベースのフラットな Markdown ファイルに変換。各ファイルには日付・プロンプト・回答を機械的に埋め込み、`topic` と `tags` は空欄にしておく。
  2. **Phase 2: AI による分類**: Claude Code にディレクトリ単位で Markdown ファイルを渡し、適切な `topic` と `tags` を付与させる。または、全プロンプト一覧を Claude に渡してカテゴリ分けを依頼する。
  3. **Phase 3: ディレクトリ再配置**: 分類結果に基づいて、ファイルを適切なディレクトリに移動するスクリプトを実行。

**【抽出時の品質管理】**
- HTML エンティティ（`&amp;` `&#39;` `\xa0` など）の適切なデコード
- 改行（`<br>`）の Markdown 改行への変換
- リンク（`<a href="...">`）の Markdown リンクへの変換
- `<FollowUp>` ブロックの特別扱い（引用ブロックとして保持するか、単なるテキストとして埋め込むか）
- エンコーディング: 入力 HTML は UTF-8。出力 Markdown も UTF-8。

**【上位目標との関係】**
この論点は「実際にデータを整理可能な形に変換する」という実践的なステップ。変換の品質が低いと、後続の Objibian での閲覧体験が損なわれるため、「綺麗に整理できる状態」を実現するには丁寧な変換が必須。

5. **Objibian（Obsidian）との統合設計**

**【論点の位置づけ】**
このプロジェクトの上位 STRATEGY「objibianで綺麗に勉強した知識を整理できる状態にする」を直接実現する論点。ディレクトリ構造と Markdown ファイルが、Obsidian の機能（グラフビュー、バックリンク、Dataview、タグ、検索）とどのように連携するかを設計する。

**【Obsidian の関連機能と設計への影響】**
- **Vault 内の配置場所**: 既存の Objibian Vault がどこにあるか、その中に `google-ai-history/` ディレクトリを作るのか、独立した Vault にするのか。上位 GOAL が「Objibianで知識を整理」なので、既存の知識ベースと同じ Vault 内に置くことで分野横断的なリンクが可能になる。
- **グラフビュー**: `[[内部リンク]]` を活用することで、質問同士の関連性がグラフとして可視化される。連鎖質問や関連トピックに `related` フィールドでリンクを張ると、知識のネットワークが自然に育つ。
- **Dataview プラグイン**: フロントマターの `topic` や `tags` を Dataview クエリで集計・一覧表示できる。例: `TABLE date, tags FROM "google-ai-history" WHERE contains(topic, "歴史") SORT date DESC`
- **タグシステム**: `tags` フロントマターに付与したキーワードが Obsidian のタグペインに表示され、クリックで横断検索できる。ネストタグ（`#法律/刑法` など）を使うと階層的な整理も可能。
- **テンプレート機能**: Obsidian の Templates プラグインを使えば、新しく Google AI 検索をした際に同じテンプレートで手動追加できる。
- **検索**: Obsidian の全文検索は Markdown ファイルの内容をインデックスするため、質問文や回答文の任意の単語で検索可能。

**【ディレクトリ設計と Obsidian の関係】**
Obsidian ではディレクトリ構造がそのままファイルエクスプローラーに表示される。つまり、論点2 で設計するディレクトリ構造は、そのままユーザーが日常的に眺める「知識の棚」になる。このため、ディレクトリ名はユーザーにとって直感的で、かつ定期的に見返したくなるような命名が望ましい。

6. **Claude Code からの検索・参照を容易にする仕組み**

**【論点の位置づけ】**
このタスク自体が「claude codeにGoogle AI 検索の履歴を合理的に整理するにはどのようなディレクトリがいいのかを聞く」であることからもわかるように、ユーザーは日常的に Claude Code を使って知識にアクセスすることを想定している。したがって、ディレクトリ構造は Claude Code が内容を理解しやすく、検索・参照しやすい形である必要がある。

**【Claude Code にとって扱いやすい構造とは】**
- **適度なファイルサイズ**: 1ファイルが長すぎる（数千行）と、Claude Code の Read ツールが内容を把握しきれない。1ファイルは質問＋回答の 1 エントリ分（数百〜数千字）が適切。
- **明確なファイル命名**: ファイル名に日付＋内容を示すスラグを含めることで、Claude Code が Glob で目的のファイルを探しやすくなる。例: `2026-07-27_ninchi-kino-teika-sagi.md`
- **検索可能な構造**: すべてのファイルが統一されたテンプレート（論点3）に従っていれば、Claude Code は Grep でフロントマターを検索し、特定トピックのファイル群を即座に特定できる。例: `grep -l "topic:.*法律" google-ai-history/**/*.md`
- **インデックスファイル**: トップレベルに `_index.md` を置き、全トピックの概要とリンクを列挙しておく。Claude Code が最初にこのファイルを読めば、全体像を把握した上で必要なファイルに絞って読むことができる。
- **曖昧検索への耐性**: ユーザーが「あの時調べたアレ」と言った場合でも、Claude Code が Grep でプロンプト本文を横断検索できるように、テンプレートに検索クエリそのものを必ず含める設計。

**【発展的な連携アイデア】**
- Claude Code 用のカスタムスラッシュコマンド（`/knowledge <キーワード>`）を作り、`grep`＋`Read` を自動化することも可能。
- bizyu MCP のタスクと知識ファイルをリンクさせ、「この知識はこのタスクから生まれた」というトレーサビリティを確保できる。

7. **未知の新トピック追加時の運用ルール**

**【論点の位置づけ】**
ディレクトリ構造は最初から完璧には作れない。903 件を分類する過程で、当初想定していなかったトピックが出現したり、分類の境界が曖昧で判断に迷うケースが必ず発生する。また、今後も Google AI 検索を使い続ける限り、新しいエントリは増え続ける。この論点では、**構造を硬直化させず、継続的に運用できるルール** を定める。

**【運用ルールの検討事項】**
- **Inbox ディレクトリの設置**: 新規エントリを一時的に格納する `_inbox/` ディレクトリを設ける。分類に迷ったものはここに入れ、定期的（例: 週1回）に Claude Code と相談しながら適切な場所に移動する。
- **Misc / Other カテゴリの許容**: 「どう分類しても微妙」なエントリのために `雑学・トリビア/` や `その他/` のようなカテゴリを用意しておく。完璧な分類を追求するよりも、**「どこにも入らないから整理されない」という最悪の事態を防ぐ** ことを優先する。
- **トピックの新設ルール**: あるトピックに属するエントリが一定数（例: 5件）を超えたら、新しいサブディレクトリを切る。逆に、1〜2件しかないトピックは親ディレクトリにフラットに置く。これにより、過剰な細分化（1ディレクトリ＝1ファイル）を防ぐ。
- **タグによるクロスリファレンス**: ディレクトリ階層は1つの主分類軸に過ぎない。`tags` フロントマターを活用すれば、「ヨーロッパ」でも「語源」でもアクセスできる。ディレクトリ分類の曖昧さをタグで補完する。
- **定期的な棚卸し**: 月1回、新しいエントリの分類状況と既存構造の妥当性を Claude Code とレビューする。必要に応じてディレクトリの統合・分割・リネームを行う。これは Objibian 内のファイル移動で済むため、比較的低コストで実施できる。

8. **優先順位付けと段階的整理の戦略**

**【論点の位置づけ】**
903 件を一度に完璧に整理するのは現実的ではない。時間的コストとモチベーションを考慮し、**どの順番で整理を進めるか** の戦略を立てる必要がある。この論点は「実際に着手する際の現実的なロードマップ」を提供する。

**【優先順位付けの軸】**
- **鮮度（最近のものから）**: 2026年7月の 160 件は記憶に新しいため、タグ付けやトピック分類が容易。また、最近調べた知識ほど「今すぐ使える」可能性が高い。
- **重要度（実用的なものから）**: 「認知機能低下と詐欺罪」のような実務に関わる知識は優先的に整理する価値がある。一方「マクドナルドとバーガーキングの子供」は後回しでよい。
- **容易さ（分類しやすいものから）**: プログラミング技術や語源など、トピックが明確で分類に迷わないものから着手することで、早期に達成感を得てモチベーションを維持する。
- **連鎖の有無（関連質問が複数あるものから）**: 「上野→台東区→皇居→浅草」のような連鎖質問群は、1つのトピックディレクトリにまとめることで大きな知識の塊になる。こうした「勝ち筋」から着手する。

**【推奨される段階的戦略】**
1. **Step 0: スクリプトで全件をフラット Markdown に変換する**（まず全件を機械的に処理し、「生ログ」から「編集可能な Markdown」に昇格させる）
2. **Step 1: 連鎖質問の検出とグループ化**（Claude Code にプロンプト一覧を渡し、同一トピックの連鎖質問を特定させる）
3. **Step 2: トピックカテゴリの仮決め**（全プロンプトを見渡して、10〜15程度の大カテゴリを仮設定）
4. **Step 3: 最近3ヶ月（2026/05-07、約453件）の分類**（鮮度と記憶の新しいものから着手）
5. **Step 4: 残りの過去分の分類**（2025/09-2026/04）
6. **Step 5: 運用ルールの確立と定期メンテナンスの開始**

**【上位目標との関係】**
この段階的戦略は「Objibian で綺麗に整理できる状態」を最も効率的に達成するための現実解である。完璧を目指して手が止まるよりも、**まず動く状態を作り、使いながら改善する** アプローチが、最終的な知識定着につながる。
